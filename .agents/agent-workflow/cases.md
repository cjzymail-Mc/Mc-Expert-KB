# 会话交接与流程分发案例

<a id="h01"></a>

## H01 在任务中途恢复上下文

用户指出配额用尽可以发生在施工中途，当时正好停在交接点的成功恢复不足以回答问题。留下一项可定位的进行中工作、当前版本和恢复入口，分别试交棒后重开与未交棒时中断。用户对学习型项目更看重恢复操作轻量。

在另一轮双会话接力中，用户指出交棒方还需按协议唤醒接棒方。一次回复记录了接棒方已消费返工棒；另一次只说明可以用原交接标识重发唤醒。当过程停在“已发”时，查看本轮序号、下一持有人和消费记录，再决定是否依原协议重发。两次回复报告的状态不同。

历史依据 · A739、H01-a、H01-b。

<a id="h02"></a>

## H02 把接力记录和交付验收分别核实

用户曾要求核对 planner/coder 是否按约定交接，也要核对施工成果是否达标；已经独立验过的内容只按新疑点复查。读取当前产物和上一次验收位置，把已验证、变化和仍需验证的范围写清。

历史依据 · 8 月协作验收记录。

<a id="h03"></a>

## H03 冷启动时保留可继续工作的最少事实

多次任务要求新会话能据交接材料继续。用户另要求将已封口事项从当前状态清出，并追问导致旧约束的 bug 已修复后能否撤销旧规。维护时先确认当前还有谁依赖该条，再把可恢复入口留在状态页，具体经过保留在相应历史记录。

一次迁移中，用户追问“上个模型说已复制”究竟写在哪个文件。助手澄清那段话来自会话接续摘要，没有对应的仓库交接文件。恢复时把上轮摘要当成待核对的线索，查目标文件和本轮授权，再决定是否继续迁移。

历史依据 · 7 月至 10 月交接、状态维护记录、H03-a。

<a id="h04"></a>

## H04 复盘多轮耗时，先找对运行

用户指定较早一次团队协作，纠正了按相邻运行做的复盘。助手随后报告，指定运行的验收条目指向较早的冻结任务书。一轮是否值得保留，取决于它完成了什么：首次观察真实界面解决了原先未知的问题，重复传递同一结论或等待唤醒则消耗了协作时间。用户还报告，另一项长任务曾为可延期的清理操作等待人工确认，希望放到约好的人工审核点。该等待时长为用户观察，现有证据没有独立计时验证。可延期的操作与能够继续的工作应分别登记。

历史依据 · H04-a、H04-b、H04-c。

<a id="d01"></a>

## D01 同构项目要交指南，文件名可以变化

用户希望让同事在一批同构研发项目中复跑同一份工作。同事可以使用仓库副本，各项目文件名不同，资料类型和子目录命名却很稳定。用户纠正了面向任意外部项目设计通用系统的思路，明确需要一份指南。助手报告已改为以同库案例说明如何按类型和关键词找资料，以及按什么顺序调用已有脚本。对话能确认指南的适用范围及修订说明，接收方复跑结果另行核实。

历史依据 · D01-a。

<a id="d02"></a>

## D02 开发机产线已经稳定，收包同事从哪里开始

一条资料生产流程在两个执行端先后跑通后，用户把目标转向交给同事稳定使用，并指出目标电脑的依赖安装情况不同。另一次工具交付中，用户允许从记录的来源取得外部依赖，要求在说明中讲清目标机自己的网络设置和登录状态。助手分别报告开始清点目录，以及已经在接收说明标出本地准备步骤。接手验收应从同事取得的实际包开始，验证取得依赖、建立本地设置、运行首个样本的全程。现有记录未验证所有接收端已成功。

历史依据 · D02-a、D02-b、D02-c。

<a id="d03"></a>

## D03 从个人使用走向同事维护，何时增加接口

用户描述了三个阶段。先亲自跑通业务，接着把技能或代码包分享给同事继续开发，出现规模化分发或长期开发需要时再考虑服务接口。助手建议先梳理稳定的任务级输入输出，把业务实现和对外调用方式分开。范围判断应写清本阶段接手者、其首次要执行或修改的业务，以及新增接口能消除哪项真实维护成本。该轮是设计咨询，未据此认定接口已建设或投入运行。

历史依据 · D03-a。
