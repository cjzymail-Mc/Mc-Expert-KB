# today（读 todays-task.md 并执行）

读取 todays-task.md,执行其中任务。

> **全托管模式横跨本 skill 三处**——§1 前置选择 / §2.2 执行期延伸 / §3.2 安全阀熔断——是同一个开关的三面。改任一处须同步另两处,避免模式语义割裂(读者会把延伸/熔断当独立逻辑)。

## §1 决策门控 · 第 0 步全托管前置门(每次运行先问,先于一切路由)

用 AskUserQuestion 让用户二选一,选定前不动手;默认/安全档 = 否:
- 〔1 · 否(默认)〕普通 /today——下方门控里"该问你"的决策点照常停下问你。
- 〔2 · 是 · 全托管(与 /team-task 深度放权(B) 同原则:不确定也先跑)〕本次运行把**门 3 的中等档决策、外加简单任务执行途中临时冒出、本来要停下问你的决策点(见 §2.2 全托管延伸)**托管给 mc-expert:其「建议」当作有约束力、直接照办继续,不再回头问你。**mc-expert 置信低/无先例时也不升级你**——它仍会给一个具体默认推荐(默认>成功率最高>最易回滚,见其铁律 2),直接采纳继续,把该裁决记进收尾「自主裁决」清单供你事后批量复盘。**仅 4 条红线才停下问你**:① 销毁性/不可逆操作(多文件删除/覆盖无备份——本就在 delete-guard 兜底层拦);② 对外交付物 / Ldterm 明文合规红线;③ 连失 2 次熔断(见 §3.2);④ 推翻 KB `decisions/` 已封决策(注:"无先例"自走,但"要推翻已封决策"仍停)。**①②类会触发权限框的命令(rm/删除/无备份覆盖/伸 `~/.claude`·系统·敏感目录/对外)绝不在全托管自主流程中途发起——会死等缺席用户 + 死锁后台 agent;一律攒「待人工处理」后置到人工门,halt 走「不执行该命令 + 落盘报告 + 上报」、不靠阻塞式权限框(后置的是决策权,非后置着自己补做);forensic/排查也不例外。详见 KB `decisions/autopilot-defer-perm-to-human-gate`。**门 1/门 2/门 4 行为不变(尤其门 2 升级到 team 始终留给你)。**全托管压的是「循环内决策门」(门 3 中等档 + 途中临时决策点),不压「用户在 todays-task.md 里显式定义的交付/验收门」(如素材审核门 / 成品人工验收)——这些照常停下、产出给用户验收,全托管不替你跳过、也别把验收门误当循环决策吞掉。**
用户没明确选"是"就按"否"执行。仅对实验性、用户已自评安全的任务才该选"是"。

## §2 执行调度

### §2.1 强制门控(读完 todays-task.md 后,先做路由判断,再动手)

1. 任务是否匹配已有 role(builder/researcher/converter/archivist/pm)或 skill?
   - 是 → 立即调用对应 slash command,不要从零规划、不要自己先读项目文件
   - 否 → 进入下一步
2. 【team task 门】任务是否是「多步实现类、需要 plan→挑刺→实现→复审」的活,或要改多文件/有架构取舍、值得 planner/mc-expert/coder 小队?
   - 是 → **停下,不要自己建队、也不要自己直接开干**;向用户说明「此任务复杂度够 team,建议走 /team-task(原生 coder 小队)」+ 一句理由,等用户确认后再动。用户拍板走才进 team-task 流程(含第 0 步 A/B 驱动模式选择)。**全托管也不例外**:升级到 team 是难度判断、始终留给用户;第 0 步选了"是"也不要自动闯过去、不要替用户决定转不转 team。
   - 否(轻量任务,单点改动/查询) → 进入下一步,自己干
3. 【mc-expert 咨询门 · 中等档(team 与单干之间)】没够 team 门、本可自己干,但**你拿不准 / 犹豫不决**,或命中 mc-expert 任一触发条件——**重大技术选型 / 改核心文件(CLAUDE.md、本 repo 的 plan*.md / agent 定义 / 若是 KB repo 则含 principles·reflexes·repo-map·decisions·references)/ 同一问题已连续失败 2 次**——则**别完全单干**:先 `Task(subagent_type=mc-expert)` 咨询(带改动背景),拿到「历史依据+建议+风险+置信度」再动手或再收尾。
   - **第 0 步选"否"(默认)**:mc-expert 置信度低时按其建议升级给用户;真正琐碎、无疑义的改动才直接自己干。
   - **第 0 步选"是"(全托管)**:拿到裁决后**直接照办、继续往下,不回头问用户**。**置信低/无先例不再升级**——采纳 mc-expert 的默认推荐(默认>成功率最高>最易回滚)继续,记进收尾「自主裁决」清单。只有 4 条红线才停(见 §1:销毁性删除 / 对外交付·Ldterm 明文 / 连失 2 次 / 推翻已封决策)。**连失 2 次熔断优先**:计数到 2 一律转人工审,不再让 mc-expert 续命(见 §3.2)。
   - 注:本门是开工/收尾前的**自觉前门**;若本 repo 装了 mc-expert Stop-hook,收尾时还有 harness 兜底,两者互补——不要因为有 hook 就在该犹豫时跳过咨询。
4. 任务是否需要盘点多个相关文件(skills/agents/templates/pipeline 等)才能动手?
   - 是 → 派 1 个 Explorer subagent 一次性平行盘清楚,不要自己串行 Glob+Read
   - 否 → 自己直接动手

### §2.2 全托管延伸 · 简单任务执行途中冒出决策点(仅第 0 步选"是"时生效)

> 全托管三面之二(之一见 §1、之三见 §3.2)。

- 场景:任务在门 2/门 3 判为轻量、已走"自己干",执行途中却临时冒出一个本来要停下问你的决策点(A 还是 B / 要不要顺手改某处 / 口径拿不准)。门 3 是开工前的前门,接不住这种途中才浮现的;本条专补这段。
- 第 0 步"否"(默认):照常停下问你,行为不变。
- 第 0 步"是"(全托管):**别停下问用户**——先 `Task(subagent_type=mc-expert)` 带背景把这个决策点丢过去咨询,拿「历史依据+建议+风险+置信度」后直接照办、继续往下。**置信低/无先例同样不升级**,采纳其默认推荐继续 + 记进收尾「自主裁决」清单;口径同门 3——只有 4 条红线才停,连失 2 次熔断优先,转人工审(见 §3.2)。
- 边界:只接管"本可自己拍的小决策"。若该决策点意味着任务其实升格到 team(改多文件 / 架构取舍),回门 2——升级到 team 始终留给你,全托管不闯。

### §2.3 效率规则

- todays-task.md 直接引用的文件(如 mc-debugN.md)和它在同一条消息里并行 Read;路径未知必须 Glob 时,Glob+Read 串行可接受
- 扫描/查找/盘点类只读动作派给 Explorer subagent(单点 1 个、多角度并行多个),不要自己 Glob/Grep 翻
- 写文件、改代码、跑命令仍由你自己执行,不委托 Explorer

### §2.4 通信规则

- 不要复述 todays-task.md 内容,直接说"开始执行 X"后动手
- 收尾只报:完成了什么 / 卡点 / 下一步建议,不要列过程清单
- **全托管额外**:收尾必在交付汇报里**显眼**附一份「自主裁决」清单(每条:决策点 / 候选 / 选了哪个 / 依据(默认|成功率|易回滚) / 置信度),供用户验收时一句话能翻、一次性批量复盘——放权的对价是**留痕浮到交付物**,不是埋进内部文件、也不是过程中逐条确认。

## §3 收尾固化

### §3.1 微型 loop:mc-update → pin → session-new(每次正常收尾必走)

todays-task.md 任务**正常收尾**后(完成、或带卡点上报但未熔断),不要就此结束——按 **mc-update → pin → session-new** 顺序跑一遍收尾固化。三个环节都是**先预判、再决策执行**,不是无脑跑;目的是省掉你每次手敲 `/mc-update`、`/pin`、`/session-new`,并把本次任务里 **capture_hook 词表漏网的纠正**捞进 feature-05 捕获网(pin 段职责)。**session-new 段现含第 0 步主线回顾**(读主线锚点→评估偏离→判下一步是否已落 plan→写进 plan),让收尾 loop 自驱推进主线下一步、不靠你人工追问;主线判断归 session-new 内部,today 不替它判(守两层判断边界)。

**触发边界**:
- 正常收尾(完成 / 带卡点上报)→ 进本 loop。
- **熔断 / halt 交用户 / 任务无实质进展** → **跳过 mc-update 和 pin**(mc-update 纪律就是"只在任务完成后走"、pin 是"捞本次纠正残留"——未完成/无产物两段都没意义);但 **session-new 仍走**——预判里点明"本次未正常完成,建议 session-new 固化中断/卡点现场以便接续"。

**mc-update → pin → session-new 的顺序语义**:mc-update 先固化"本次经验/记忆层";**pin 居中**——捞 mc-update 判定后仍漏网的纯陈述式纠正(若 mc-update 判"无新可固化",pin 预判多半也是"无漏网纠正");session-new 最后固化"本次讨论/状态层"做交接,并落 pin 段报告行(见下)。三者职责不重叠(mc-update 偏 memory/feedback、pin 偏 feature-05 燃料补漏、session-new 偏 plan/状态文件)。

**每个环节两步走**:

1. **预判(必带,不能套话)**:基于**本次任务的实际产物**给一句话预判——"有/没有可固化(mc-update)/ 漏网纠正(pin)的东西,建议跑/不必跑;**session-new 段判本次是否正常收尾**(正常收尾→必启动,主线/下一步判断归 session-new 内部第 0 步、不在本层判)"+ 一句**具体理由**。每次任务的明细、中间产物、来源入口都不同,预判必须落到本次实际,禁止"建议跑 mc-update"这种通用套话。
2. **决策 + 执行**:
   - **第 0 步"否"(普通模式,默认)**:用 AskUserQuestion 弹问,把预判写进选项描述(让你看着预判拍板)——**判断权在你**。选"是" → **你不再手敲**,Claude 直接用 Skill 工具调用 mc-update / session-new 执行(pin 段见下、走陪审通道)。选"否" → 跳过。
   - **第 0 步"是"(全托管)**:不弹你,把"要不要跑 mc-update / session-new"+ 任务背景/产物丢给 mc-expert 咨询,它判定后 Claude 直接照办(跑或跳),记进收尾「自主裁决」清单。**熔断场景仍按上面"触发边界"处理**——不让 mc-expert 给 mc-update 续命。

**★ pin 段(居中 · feature-05 补漏层)**——**判据单一指针见 KB `Mc-Expert-repo/references/收尾loop判据.md`**(PIN/DROP 判据、方案 a 去重、掉线降级、陪审 spawn 五要素都在那;本命令只写控制流、不抄判据,改判据只改那一处):
1. **预判闸(必带)**:一句话判"本次有无词表漏网的纠正迹象"——**无迹象直接跳 pin 段、不派 mc-expert**(省陪审成本,实测一次约 2m56s+token)。有迹象才往下。
2. 有迹象 → 回顾本次任务列纠正候选(**认不出不硬造**,pin.md 铁律)。
3. **去重(方案 a)**:Grep/Read 本会话 `live-candidates.<session>.jsonl`,capture_hook 已抓的剔除(pin_capture.py 跨文件不去重,必须 LLM 自查)。
4. **派 mc-expert 陪审**:候选 ≥2 条一次 spawn 全给、逐条判;单条才单发。spawn prompt 五要素 + 红线"只给 PIN/DROP+依据、不复述纠正、不顺势修错、**不附概率分**"见判据指针 §5。
5. **掉线降级**:mc-expert 零正文 / Connection closed → 重试 1 次 → 仍失败 → 该候选落 `Loops/review-queue.md` 交用户补判(**不硬 pin、不 DROP、不连试 ≥2 次**,细则见判据指针 §4)。
6. **落账**:只对陪审 PIN 的跑 `pin_capture.py`(`--corr`/`--ai`/`--note`/`[--followup]`);lead 调用前自校验 fail-loud(陪审缺 PIN/DROP/纠正原文/依据 → 不硬凑参数,见判据指针 §6);候选为空 → 静默跳过。
7. **报告行**:pin/drop/掉线降级任一发生 → 在 session-new 段产出的 plan 里记一行 `pin N / drop M / 降级 K 落 review-queue`(漏跑频率可观测,供决定是否上路线 C Stop hook)。

**一致性约束(堵 temp.md 实证偏差:B 模式下 claude 曾自判跳过、没派 mc-expert)**:
- 收尾三段**每段预判一句话 + 跳过必给具体理由**,不许"看起来没什么"的套话跳过。
- **第 0 步"是"(全托管)下,pin 段预判闸判"无迹象"可直接跳**(这是基于产物的事实判断、不是偷懒);**但只要"有迹象"就必须派陪审、不许自判"算了不 pin"**——这是规则在场仍被违反的点,靠本 checklist 收窄走样空间,**但不保证**(temp.md 已证软自律不保证必跑;要保证"必跑收尾"只能路线 C,本版未实现,此为已知缺口)。

**两层判断边界(别越权)**:本 loop 只判"**要不要启动** mc-update / pin / session-new"。启动之后——写不写记忆、pin 哪条、产不产 plan——是 mc-update / pin_capture / session-new **各自流程的职责**(mc-update 有频次/去重两道闸门、pin 走判据指针、session-new 有自己的四步),today 收尾不替它们判、也不重复其内部逻辑。

**全托管下 session-new 的边界**:mc-expert 判"跑 session-new" = 走固化交接流程(产 plan + 更新状态文件),**不是强制清空/重开 session**——真正关 session、重开仍由你操作,mc-expert 不替你决定何时真关。

**session-new 段幂等(防 loop 重入产重复 plan)**:session-new 重入前查本会话 plan 是否已存在(同名/同任务)——存在则**只跑第 0 步主线回顾 + 状态更新、不重复产 plan**(不再整个跳过,否则主线回顾也漏)。

### §3.2 全托管安全阀 · 连续失败 2 次 → 转人工审(仅第 0 步选"是"时生效;触发于 §2 每步判定后)

> 全托管三面之三(之一见 §1、之二见 §2.2)。

- 为什么用脚本:阈值计数不能靠你自己记(context 压缩会丢计数、"再试一次"会越过阈值)。确定性交给计数文件 + 固定脚本,你只负责"认这次成/败"。
- 脚本:`pwsh -File "$env:USERPROFILE\.claude\commands\autopilot_failcount.ps1" -Mode <reset|fail|status>`(经 junction 解析到 KB repo,换机/换账号都通)。
- 全托管开跑**先 `-Mode reset` 清零**。
- 每个任务步骤判定后:这步**确实失败**→跑 `-Mode fail`;**确实成功**→跑 `-Mode reset`(连续失败,成功即断 streak)。成/败是你的语义判断,不是每个微动作都记。
- 脚本累计达 2 时输出 `AUTOPILOT_STOP`(带 🛑)并退出码 2:**见到 `AUTOPILOT_STOP` 或退出码 2,立即停止本次执行,把现状 + 卡点交用户,不得再试第 3 次**——要不要继续不由你判断。
- 兜底层不变:delete-guard hook + 权限方案 A 仍在 agent 层之下拦危险动作,全托管不放宽。
